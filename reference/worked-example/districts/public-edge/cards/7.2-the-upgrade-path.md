# 7.2 · The Upgrade Path

**Type + State:** INSTRUCTION · LIVE — it directs a human, and no run reads it: the root `README.md`
tells users to upload `specialist/` only (`README.md:96-99`), so the file that carries these
instructions never reaches a conversation. Delete them and no answer changes.

**What it is:** three instructions that move a user's own region files across versions — from v1
(`README.md:217`: drop the old `region/` files into v2, "Everything else upgrades cleanly"), to each
later release (`:272`: replace `specialist/` except `reference/region/`, keep the populated
`region/`), and from an example (`:234`: copy a case study's `region/` over the blank, as-is).

**Why it is shaped that way:** the engine is the same for everyone and the region is each user's
own work, so an upgrade replaces the one and keeps the other.

**Source path:** `README.md`

**Hits:** the user, at their next upgrade — and through them every deployed market, because the
region files they kept meet the new engine with nothing checking that the two still fit.

**Does not hit:** the region packs. No step rewrites them, which is the point — and the trap. An
engine release that renames a section it reads (card 02 lists every one) reaches no kept pack, so
"upgrades cleanly" stops being true without a word. A user who copies Lisbon as-is (`:234`) gets a
market with no seasonality section for `frameworks/pricing.md:80` to apply.

**Done when:** you can say which of the three instructions your user follows and what it keeps. If
your change is to the engine, check card 02's list before calling the upgrade clean. Stop there.
