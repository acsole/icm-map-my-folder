an instrument, not a document

A map of your folder, for the reader who has no memory.

Drop it into a Claude Project, point it at your own folder, and it produces a catalog and a handful of cards — each one shorter than the file it points at. Its purpose is narrow: let a later reader change one thing without reading everything.

Load the catalog, then one card. Never the whole folder.

A map you have to read in full is a folder you have to read in full, with an extra step. If a question needs a second card, the first card was mis-scoped — that is a defect in the map, not permission to keep reading.

Watch a folder get mapped.

One real repository, eight named stages: enumerate, find the repeating unit, classify, date every verdict with the command that decided it — then answer a question and stop.

Eight stages, the real artifact of each on screen. Captions carry the spoken track, which speaks each stage's on-screen headline and nothing else.

Seven card types. A closed set, each with a proof test.

Not adjectives — checks. A noun that fails all seven gets no card; it gets one line in the notes. That refusal is what keeps a map smaller than its territory.

TypeProof testWhat it hits
ENGINETwo or more instances read it. Change it and all their behavior changes.every instance, in place
BLUEPRINTInstances contain its text rather than reference it.future copies only
INSTANCEIt has a name an outsider recognizes — a market, a client, a product.nothing; it is a leaf

SURFACESomeone who never opened the folder can encounter it.outsiders, after publish

State is a second axis, and appearance never decides it.

Type says what a thing is. LIVE / LEFTOVER / GHOST says whether it is still alive — and no verdict ships without the command, path or status code that decided it.

the inversion rule

Look for who reads it first.

Big, current, well-written, and nothing reads it. Four lines the machinery branches on. A folder full of real data that the machinery never resolves into. Recent edits are evidence about an author, never about a reader.

evidence, in the same line

Or the verdict is UNVERIFIED.

A command and its output, a file:line, a status code, a byte count, a commit SHA. Not “appears unused”, not “looks legacy”. An honest gap is a map entry; a guess is a defect.

Two walks, kept apart.

They run in opposite directions and conflating them is the failure mode: a reading step inside a map-making pass writes cards before the collision pass; a map-making step inside a read turns a two-hop answer into a tour.

walk a — making the map

Cards are step seven.

  1. Enumerate — never guess a filename
  2. Find the repeating unit
  3. Classify by type
  4. Mark state, with evidence
  5. Collision pass
  6. Trace propagation: copy or reference
  7. Cards, last

Done when the checks pass.

walk b — reading the map

Most reads stop at two.

  1. Catalog
  2. One card
  3. Its Hits line — only if you are changing something
  4. Stop

Done when the question is answered.

the hardest line is “does not hit”

It must name the noun a reader reaches for first and wrongly, and it must be mildly surprising. If you cannot name a plausible wrong reach, the card does not get written — that check alone deletes most of the cards a model would otherwise produce.

Two refusals. One of them runs.

No photocopy — three checks, all executable, plus the precedence line: if a card and the file disagree, the file wins and the card is wrong. No slurping — answering costs a catalog and one card; when mapping, you enumerate paths and sizes before opening anything.

Each broken card is broken in one way only, and the test passes only if it trips exactly that check. The cards live in reference/checks/fixtures/refusal/, so anyone can see the red before trusting the green.

the cold run ships with it

With the catalog loaded — the configuration the README specifies — a fresh session with no memory and no coaching was asked “What is Services?”: it opened one card, answered with the collision, the routing row and a counting defect the repo did not know it had, and stopped. Runs given no framing at all took four reads; the transcript carries all three, including the one that never found the catalog and is the reason the door exists. Re-run any of them yourself — the configuration is a flag on the shipped tool, CATALOG_IN_CONTEXT=1.

A change question costs more than an identification one, by design — the walk says to read a card's Hits line only when you are changing something. Measured, same configuration: “I want to edit region/market.md — what else changes?” took one card plus the file itself. The same question with no framing at all took twelve.

and now it can be checked without a key

The cold run is two steps. cold-run.py needs the API and is run once: it records each walk as JSON, with the hash of every file the model opened. score-walk.py needs nothing installed: it reads those records and checks six things — that the walk is of this version of the map, that it reached the right card, kept to its budget, stayed out of the territory, stopped on its own, and gave the right answer. Its own --self-test shows each of the six failing on a broken record first. The runs described above predate the recorder, so they are not scored; until new ones are recorded, the verdict says fail, and that is the honest reading.

What it refuses to map.

  • 01A pile of one-offs. No repeating shape, so every card would be a summary. ls -lt is cheaper and tells you more.
  • 02A single application where every file is unique. Nothing is copied, so nothing propagates. That wants a call graph.
  • 03The methodology itself — a folder system about folder systems, this repo included. Mapping a method with the method returns a mirror.
  • 04Anything it found broken. It marks the ghost and leaves it. A map that edits its territory while drawing it is a map of something that no longer exists.
